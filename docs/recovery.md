# 백업·업데이트·복구 검증

공식 실행 결과와 미검증 환경은 [#5](https://github.com/river11456/mundok/issues/5)에 기록한다. 이 문서는 반복 실행할 절차다. 사용자 실데이터 대신 `test/fixtures/backup/`의 합성 표본을 사용한다.

## 백업 호환 범위

앱 버전 `2.4.1`, 문헌 `schemaVersion: 3`, 전체 백업 `version: 3`은 서로 다른 버전이다.

| 입력 | 복원 범위·변환 | 한계 |
| --- | --- | --- |
| v3 전체 백업 | 문헌·수정 카드·문법·해석 순서·폴더·학습 로그·세션·설정 | 덮어쓰기이며 병합·부분 복원 UI는 없다 |
| collections 없는 구 v3 | 문헌 등을 복원한 뒤 다음 시작에서 카탈로그 기본 폴더를 시드 | 백업에 없던 사용자 폴더 위치는 재현할 수 없다. `collections: []`는 빈 폴더로 유지 |
| v2 키 덤프 | `hanja-v2/*`를 복원하고 다음 시작에서 번들 8문헌·델타·사용자 문헌과 학습 기록을 이전 | v1 실패 횟수는 `legacy` 요약 로그로 이전하며 과거 개별 복습 이벤트를 재구성하지 않는다 |
| userdata 단일 객체 | 추가·수정·삭제·문법·해석 순서 델타를 구 번들 문헌에 적용 | 단독 파일에는 사용자 문헌·학습 기록·폴더가 없으므로 전체 백업과 동등하지 않다 |

문헌 하나의 JSON 내보내기는 전체 백업이 아니다. 임의의 미래 버전·손상 파일은 지원 범위가 아니다. 현재 입력 검사는 완전하지 않다([#17](https://github.com/river11456/mundok/issues/17)).

## 합성 표본과 자동 검사

- `v3.json`: 문헌 2개, 수정 카드·삭제 표시·문법·해석 순서, 부모/자식 폴더, 로그·세션·설정.
- `v2.json`: 구 키 덤프, 카드 델타, 사용자 문헌, 실패 횟수·마지막 세션·설정.
- `legacy-userdata.json`: v2 표본과 같은 카드 델타만 담은 구 형식.
- `catalog.json`: 자동 테스트에서 사용하는 합성 구 번들. 실제 앱의 8문헌 번들을 대체하지 않는다. 따라서 v2/단일 userdata 표본의 `sample` 문헌 델타는 실제 앱 UI에서 이전되지 않는다. 실제 8문헌 이전의 UI 검증은 해당 문헌 ID를 사용한 별도 표본이 필요하다.

```sh
node --experimental-strip-types --test test/backup-recovery.test.mjs
npm run lint
npm test
npm run build
```

Node 22.18 이상에서 실행한다. 테스트는 실제 가져오기·내보내기·마이그레이션 함수를 사용하고 저장소와 다운로드 수단만 대체한다. 초기화 함수 재호출은 브라우저 프로세스 재시작을 대신하지 않는다. 정상 왕복은 내보낸 시각을 제외하고 모든 백업 필드를 비교한다.

`KNOWN DEFECT` 테스트는 아래 결함이 여전히 재현됨을 뜻한다. 통과를 데이터 보존 보장으로 해석하지 않는다. 수정 이슈에서 원본 보존·입력 거부의 회귀 테스트로 전환한다.

- [#16](https://github.com/river11456/mundok/issues/16): 중간 쓰기 실패 시 기존 데이터 삭제 및 부분 복원.
- [#17](https://github.com/river11456/mundok/issues/17): 잘못된 카드·로그 구조가 검사를 통과.
- [#18](https://github.com/river11456/mundok/issues/18): 구 백업 복원 시 기기에 남은 v1 문헌·기록 혼입.

## 브라우저 복원·업데이트 재실행

1. 사용자 운영 주소와 다른 전용 로컬 주소 또는 비어 있는 테스트 프로필을 사용한다. 기존 사용자 저장소를 지우거나 덮어쓰지 않는다.
2. 검증할 두 GitHub Release의 `artifact.tar`를 각각 빈 디렉터리에 받고 Release에 표시된 SHA-256과 대조한다. 구 버전을 로컬 서버로 연다. 같은 호스트·포트를 끝까지 사용한다(`localhost`와 `127.0.0.1`은 다른 저장소다).
3. 빈 라이브러리·온보딩을 확인한다. 백업 메뉴에서 `v3.json`을 가져온 뒤 부모 → 자식 폴더의 문헌 2개, 합성 문헌 카드 `甲甲`의 `독음 / 사용자 수정 / 메모`, 이어하기와 연속 학습 4일을 확인한다.
4. 내보내기로 안전 사본을 브라우저 밖에 보관한다. 새 테스트 프로필에서 그 파일을 가져와 동일 데이터를 확인한다. 파일 다운로드 완료 여부와 내용 비교도 기록한다.
5. 기존 프로필을 유지한 채 서버만 새 출시 디렉터리로 바꾼다. 재접속 후 새 버전 표시와 폴더·수정 카드·학습 상태를 확인한다. 캐시 때문에 첫 화면은 구 버전일 수 있으므로 갱신에 필요했던 재접속 횟수를 기록한다.
6. 새 버전이 온라인에서 열린 뒤 서버를 중지하고 재접속한다. 홈, 폴더, 설치 문헌, 이어하기와 정답 보기를 확인한다. **서버 중지 검사는 기기 전체의 네트워크 차단이 아니다.** 외부 폰트·최초 미방문 카탈로그의 오프라인 사용을 입증하지 않는다.
7. PC 브라우저와 iPad/폰의 설치형 PWA에서 비행기 모드·앱 종료/재실행·파일 선택/다운로드를 각각 확인한다. 화면 크기 흉내만으로 실제 기기 검증을 대체하지 않는다.

기록할 값: 날짜, OS·브라우저·설치 형태, 구/새 버전·전체 SHA·Release/배포 실행 링크, 표본, 기대값·실제값, 재접속 횟수, 실패·미검증 범위. 모든 카드 ID·로그의 동일성은 UI 표시만으로 판단하지 않고 내보낸 파일을 비교한다.

## 데이터 복구 절차

1. 오류가 나면 덮어쓰기 재시도와 사이트 데이터 삭제를 멈춘다. 기존의 정상 백업을 보존한다. 실패 후 내보낸 파일은 별도 이름으로 저장하며 정상 사본을 대체하지 않는다.
2. 오류와 앱 버전을 기록하고 정상 백업을 별도의 비어 있는 테스트 프로필에서 검증한다. 현재 저장소가 불안정하면 같은 환경에서 반복 복원을 시도하지 않는다.
3. 저장 가능한 환경에서 검증된 정상 백업을 가져오고 재접속한 뒤 문헌·수정·폴더·학습 기록을 확인한다. 다시 내보내 내용도 대조한다. 백업이 없다면 직접 작성·수정한 내용과 학습 기록의 복구를 보장할 수 없다.
4. 자동 검사의 `recovery drill`은 중간 쓰기 실패를 발생시킨 후 저장이 가능해진 환경에서 **실패 전에 내보낸 사본**을 복원하여 전체 데이터 왕복을 확인한다. 실제 브라우저의 용량 확보·저장 권한 복구는 별도 검증이다.

## 앱 되돌리기 판단

앱 산출물 되돌리기는 사용자 데이터 복원이 아니다. 이전 Release의 SHA와 산출물, 읽을 수 있는 저장·백업 형식을 먼저 확인한다. 현재 데이터를 내보내 별도 프로필에서 이전 앱으로 열고 재시작·재내보내기를 확인한 뒤에만 운영 복구 대상으로 판단한다. 이전 앱이 새 형식을 읽지 못하면 사용자 저장소를 유지한 채 앱만 되돌리지 않는다. 운영 배포는 PROCESS.md의 출시 판단과 기록을 따른다.

#5에서 수행한 2.4.0 → 2.4.1 로컬 갱신은 운영 롤백 실행이나 모든 이전 버전의 호환 보장이 아니다.
