# 백업·업데이트·복구 검증

공식 실행 결과와 미검증 환경은 [#5](https://github.com/river11456/mundok/issues/5)에 기록한다. 이 문서는 반복 실행할 절차다. 사용자 실데이터 대신 `test/fixtures/backup/`의 합성 표본을 사용한다.

## 백업 호환 범위

이 문서의 코드 기준은 아직 출시 완료를 뜻하지 않는 **3.0.0 수정본**이다. 앱 버전 `3.0.0`, 문헌 `schemaVersion: 3`, 전체 백업 `version: 3`은 서로 다른 버전이다.

| 입력 | 복원 범위·변환 | 한계 |
| --- | --- | --- |
| v3 전체 백업 | 문헌·수정 카드·문법·해석 순서·폴더·학습 로그·세션·설정 | 덮어쓰기이며 병합·부분 복원 UI는 없다 |
| collections 없는 구 v3 | 문헌 등을 복원한 뒤 다음 시작에서 카탈로그 기본 폴더를 시드 | 백업에 없던 사용자 폴더 위치는 재현할 수 없다. `collections: []`는 빈 폴더로 유지 |
| v2 키 덤프 | `mundok-v3/*`·`hanja-v2/*` 키 덤프를 복원. 구 키는 다음 시작에서 번들 8문헌·델타·사용자 문헌과 학습 기록으로 이전 | v1 실패 횟수는 `legacy` 요약 로그로 이전하며 과거 개별 복습 이벤트를 재구성하지 않는다 |
| userdata 단일 객체 | 추가·수정·삭제·문법·해석 순서 델타를 구 번들 문헌에 적용 | 단독 파일에는 사용자 문헌·학습 기록·폴더가 없으므로 전체 백업과 동등하지 않다 |

문헌 하나의 JSON 내보내기는 전체 백업이 아니다. 임의의 미래 버전·손상 파일은 지원 범위가 아니다. 3.0.0 수정본은 내부 카드·로그·세션·설정 구조와 중복 ID를 검사하며, 문법·해석 좌표는 원문의 Unicode 코드 포인트 길이 안에 있는 안전한 정수만 허용한다. **과거 앱에서 원문을 수정한 뒤 범위 밖 주석이 남은 백업도 거부될 수 있다.** 원본 파일을 보관하고 별도 사본의 좌표를 보정한 뒤 검증한다. 자동으로 잘라내거나 버리지 않는다.

## 합성 표본과 자동 검사

- `v3.json`: 문헌 2개, 수정 카드·삭제 표시·문법·해석 순서, 부모/자식 폴더, 로그·세션·설정.
- `v2.json`: 구 키 덤프, 카드 델타, 사용자 문헌, 실패 횟수·마지막 세션·설정.
- `legacy-userdata.json`: v2 표본과 같은 카드 델타만 담은 구 형식.
- `catalog.json`: 자동 테스트에서 사용하는 합성 구 번들. 실제 앱의 8문헌 번들을 대체하지 않는다. 따라서 v2/단일 userdata 표본의 `sample` 문헌 델타는 실제 앱 UI에서 이전되지 않는다. 실제 8문헌 이전의 UI 검증은 해당 문헌 ID를 사용한 별도 표본이 필요하다.

```sh
node --experimental-strip-types --test test/backup-recovery.test.mjs test/backup-validation.test.mjs test/editing-session.test.mjs
npm run lint
npm test
npm run build
```

Node 22.18 이상에서 실행한다. 테스트는 실제 가져오기·내보내기·마이그레이션 함수를 사용하고 저장소와 다운로드 수단만 대체한다. 초기화 함수 재호출은 브라우저 프로세스 재시작을 대신하지 않는다. 정상 왕복은 내보낸 시각을 제외하고 모든 백업 필드를 비교한다.

수정된 회귀 검사는 다음 계약을 확인한다. 브라우저·실제 기기 검증 결과는 별도로 기록한다.

- [#16](https://github.com/river11456/mundok/issues/16): 복원 도중 각 저장 연산 실패 시 원본 보존, 계속되는 실패 시 저널 유지, 다음 초기화의 복구, 마이그레이션 실패 시 입력 원시 데이터 보존.
- [#17](https://github.com/river11456/mundok/issues/17): 잘못된 카드·로그·좌표 등을 쓰기 전에 거부.
- [#18](https://github.com/river11456/mundok/issues/18): 구·신 저장 영역을 함께 교체해 백업에 없는 이전 문헌·기록이 다시 나타나지 않음.

## 저장 보호와 호환 경계

가져오기 전에 `mundok-v3/*`와 `hanja-v2/*`의 원본 키·값을 `mundok-backup/restore-journal`에 저장한다. 이 사본을 담을 **추가 localStorage 공간**이 필요하며 공간이 부족하면 원본 교체 전에 중단한다. 교체 중 실패하면 원본으로 되돌리고, 되돌리기도 실패하면 저널을 유지한다. 다음 시작은 저널 복구를 먼저 수행한다. 정상 작업이 끝나면 저널을 제거한다. 사이트 데이터 삭제는 이 사본도 삭제하므로 복구 방법이 아니다.

가져오기와 다음 시작의 마이그레이션은 별도 트랜잭션이다. 가져오기가 실패하면 가져오기 전 원본을 보존한다. 가져오기가 성공한 후 마이그레이션이 실패하면 **받아들인 백업의 원시 키**를 보존해 다시 이전할 수 있게 한다. 가져오기 전 데이터로 되돌아가는 계약은 아니다. 초기화 전에 저널 저장이 실패해도 원시 키를 복구 사본으로 내보낼 수 있다.

앱은 페이지 수명 동안 Web Locks 잠금을 유지해 **같은 origin에서 한 창만 편집**하도록 한다. HTTPS 또는 localhost에서 Web Locks를 지원하는 브라우저가 필요하다. 미지원·권한 거부·다른 창 점유 시 초기화를 중단하고 재시도를 안내한다. 이때 복구 사본 버튼은 표시하지 않는다. 구버전 창은 이 잠금에 참여하지 않으므로 **가져오기 전에 다른 문독 탭과 설치형 앱 창을 모두 닫는다.**

## 로컬 브라우저 저장 실패 검사

`test/browser-backup-recovery.html`은 Vite 개발 서버에서만 쓰는 검사 페이지이며 운영 산출물에 배포하지 않는다. **사용자 데이터가 없는 새로운 localhost 포트(origin)**에서 합성 표본만 사용한다. 기존 운영 프로필이나 사용자 주소에서 실행하지 않는다.

1. `npm run dev -- --host 127.0.0.1 --port 45106 --strictPort`처럼 사용하지 않은 포트로 실행하고 `http://localhost:45106/test/browser-backup-recovery.html`을 연다. 같은 origin의 다른 문독 창은 닫는다.
2. **정상 복원·잘못된 입력·실제 용량 초과 검사**를 누른다. v3 표본 복원, 잘못된 범위 거부, 실제 저장 용량 초과 시 원본 보존, 복구용 v2 키 덤프 왕복, 구 v2/userdata 복원 후 잔여 문헌·기록이 섞이지 않는 결과를 확인한다. 용량 채우기용 키는 검사 후 제거한다.
3. **중단된 복구와 용량 부족 준비**를 누르고 **앱 열기**로 이동한다. 저장 오류 화면과 복구 사본 내보내기·재시도 버튼을 확인한다. 다운로드 파일 자체의 확인 여부도 별도로 기록한다.
4. 같은 탭에서 검사 페이지로 돌아와 **테스트 용량 비우기**를 누른 뒤 **앱 열기**로 다시 이동한다. 저널 복구 후 부모·자식 폴더와 문헌이 돌아오는지 확인한다.
5. 앱이 열린 상태에서 같은 origin을 새 탭으로 열어 두 번째 창의 시작이 차단되는지 확인한다. 첫 창을 닫고 두 번째 창에서 재시도해 저장 내용을 확인한다.

검사 페이지의 v2 왕복은 함수를 통한 합성 데이터 검사다. 실제 파일 다운로드·파일 선택·업로드 왕복을 대신하지 않는다.

## 브라우저 복원·업데이트 재실행

1. 사용자 운영 주소와 다른 전용 로컬 주소 또는 비어 있는 테스트 프로필을 사용한다. 기존 사용자 저장소를 지우거나 덮어쓰지 않는다.
2. 검증할 두 GitHub Release의 `artifact.tar`를 각각 빈 디렉터리에 받고 Release에 표시된 SHA-256과 대조한다. 구 버전을 로컬 서버로 연다. 같은 호스트·포트를 끝까지 사용한다(`localhost`와 `127.0.0.1`은 다른 저장소다).
3. 빈 라이브러리·온보딩을 확인한다. 백업 메뉴에서 `v3.json`을 가져온 뒤 부모 → 자식 폴더의 문헌 2개, 합성 문헌 카드 `甲甲`의 `독음 / 사용자 수정 / 메모`, 이어하기와 연속 학습 4일을 확인한다.
4. 내보내기로 안전 사본을 브라우저 밖에 보관한다. 새 테스트 프로필에서 그 파일을 가져와 동일 데이터를 확인한다. 파일 다운로드 완료 여부와 내용 비교도 기록한다.
5. 기존 프로필을 유지한 채 서버만 새 출시 디렉터리로 바꾼다. 재접속 후 새 버전 표시와 폴더·수정 카드·학습 상태를 확인한다. 캐시 때문에 첫 화면은 구 버전일 수 있으므로 갱신에 필요했던 재접속 횟수를 기록한다.
6. 새 버전이 온라인에서 열린 뒤 서버를 중지하고 재접속한다. 홈, 폴더, 설치 문헌, 이어하기와 정답 보기를 확인한다. **서버 중지 검사는 기기 전체의 네트워크 차단이 아니다.** 외부 폰트·최초 미방문 카탈로그의 오프라인 사용을 입증하지 않는다.
7. PC 브라우저와 iPad/폰의 설치형 PWA에서 비행기 모드·앱 종료/재실행·파일 선택/다운로드를 각각 확인한다. 화면 크기 흉내만으로 실제 기기 검증을 대체하지 않는다.

기록할 값: 날짜, OS·브라우저·설치 형태, 구/새 버전·전체 SHA·Release/배포 실행 링크, 표본, 기대값·실제값, 재접속 횟수, 실패·미검증 범위. 모든 카드 ID·로그의 동일성은 UI 표시만으로 판단하지 않고 내보낸 파일을 비교한다.

## 데이터 복구 절차

1. 오류가 나면 반복 가져오기와 사이트 데이터 삭제를 멈춘다. 기존 정상 백업을 보존하고 다른 문독 탭·앱 창을 닫는다.
2. 저장 오류 화면의 **복구 사본 내보내기**로 v2 키 덤프를 별도 이름에 저장한다. 저널이 있으면 작업 전 원본, 없으면 현재 원시 키를 담는다. 정상 백업을 이 파일로 대체하지 않는다. 저장소 읽기 자체가 거부되거나 저널이 손상되면 내보내기도 실패할 수 있다.
3. 브라우저 저장 공간·권한을 확인한 뒤 **다시 시도**한다. 저널 복구가 끝나기 전에는 학습·편집 화면을 시작하지 않는다. 복구 저널이 남은 채로 구버전 앱을 연결하지 않는다.
4. 필요하면 복구 사본이나 정상 백업을 별도의 비어 있는 테스트 프로필에서 먼저 검증한다. 저장 가능한 환경에서 가져오기·재접속 후 문헌·수정·폴더·학습 기록을 확인하고 다시 내보내 내용도 대조한다. 백업과 읽을 수 있는 복구 사본이 모두 없으면 직접 작성·수정한 내용과 학습 기록의 복구를 보장할 수 없다.

## 앱 되돌리기 판단

앱 산출물 되돌리기는 사용자 데이터 복원이 아니다. **복구 저널이 남아 있으면 구버전으로 되돌리지 말고 현재 복구 경로를 먼저 완료한다.** 이전 Release의 SHA와 산출물, 읽을 수 있는 저장·백업 형식을 먼저 확인한다. 현재 데이터를 내보내 별도 프로필에서 이전 앱으로 열고 재시작·재내보내기를 확인한 뒤에만 운영 복구 대상으로 판단한다. 이전 앱이 새 형식을 읽지 못하면 사용자 저장소를 유지한 채 앱만 되돌리지 않는다. 운영 배포는 PROCESS.md의 출시 판단과 기록을 따른다.

#5에서 수행한 2.4.0 → 2.4.1 로컬 갱신은 운영 롤백 실행이나 모든 이전 버전의 호환 보장이 아니다.

실제 iPad/폰 설치형 PWA, 기기 전체 네트워크 차단, 실제 파일 다운로드 후 업로드 왕복은 #5의 미검증 범위로 유지한다.
